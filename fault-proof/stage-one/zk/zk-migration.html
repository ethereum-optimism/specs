Overview

Migrations to ZKDisputeGame target chains that already run super-root dispute games. A migration registers ZK_DISPUTE_GAME and makes it the respected game type.

In-Flight Withdrawal Safety

MCP clones embed the implementation address at deployment time. Old SFDG/SPDG game clones created before the migration retain their original implementation bytecode forever. New ZK_DISPUTE_GAME clones created after setImplementation() in DisputeGameFactory use the ZKDG implementation.

wasRespectedGameTypeWhenCreated is snapshotted at game creation. AnchorStateRegistry.isGameClaimValid() reads this flag during withdrawal finalization. Games created under the old respected type remain valid for in-flight withdrawal finalization even after the migration.

rootClaimByChainId is declared on all game types in scope (SFDG, SPDG, ZKDG). The Portal calls it on all games whose type is in the isSuperGame allowlist. Old games already return the correct answer via their existing implementation. No special handling is needed for pre-migration games during Portal withdrawal verification.

Source-type games created after the respected game type switches to ZK_DISPUTE_GAME are not respected (wasRespectedGameTypeWhenCreated == false), so they cannot back withdrawals. Neither mechanism for switching the respected game type changes retirementTimestamp: AnchorStateRegistry.initialize() only sets it when it is zero, and setRespectedGameType() does not touch it. Games created before the switch therefore stay valid. Forming an interop set with migrate() is different: it retires all pre-migration games; see iMIG-014.

Common Mechanics

  1. Use an OPCM release that carries the ZK contracts. The release provides zkDisputeGameImpl and sp1PlonkAdapterImpl (see OPCM Integration).

  2. Register ZK_DISPUTE_GAME with OPCMv2.upgrade(). The upgrade input contains all six disputeGameConfigs. The ZK_DISPUTE_GAME entry is enabled, has a non-zero initBond, and carries abi.encode(ZKDisputeGameConfig) as gameArgs. OPCM registers the ZK game with the 3-argument overload and sets its init bond:

    disputeGameFactory.setImplementation(
    GameTypes.ZK_DISPUTE_GAME,
    zkDisputeGameImpl,
    makeGameArgs(...)  // 140-byte packed CWIA args built from ZKDisputeGameConfig
);
disputeGameFactory.setInitBond(GameTypes.ZK_DISPUTE_GAME, initBond);

    Old game clones are unaffected. New ZK_DISPUTE_GAME games use zkDisputeGameImpl.

    The same upgrade MAY disable the source game type by setting its entry to enabled = false with a zero initBond. This requires switching the respected game type in the same upgrade with mechanism 3.1, because OPCM requires the resulting respected game type to be enabled. Disabling clears the source type's implementation and init bond, so no new games of that type can be created. Existing clones keep their implementation and resolve as before.

  3. Switch the respected game type to ZK_DISPUTE_GAME with one of:

    1. the same upgrade() call, with the extra instruction key overrides.cfg.startingRespectedGameType and data abi.encode(GameTypes.ZK_DISPUTE_GAME). OPCM re-initializes the AnchorStateRegistry with it; or

    2. a later Guardian call:

      anchorStateRegistry.setRespectedGameType(GameTypes.ZK_DISPUTE_GAME);

      This lets operators register ZK_DISPUTE_GAME first and switch once honest ZK actors are running.

    Before the switch, an honest ZK proposer, prover and challenger (see Honest Actors) MUST be operational and funded. This is the chain operator's responsibility and is not enforced by OPCM.

  4. Keep the anchor state. upgrade() always re-initializes the AnchorStateRegistry, but it preserves the anchor root, the anchor game, the blacklist and retirementTimestamp. The starting anchor root cannot be overridden during an upgrade. SFDG and SPDG already commit to super roots, the same bytes32 format that ZKDG uses, so the existing anchor is a valid starting point for the first ZKDG game (parentIndex = type(uint32).max).

Migrating from a classic output-root FaultDisputeGame with upgrade() is not supported: its anchor is not a super root and cannot be re-seeded during an upgrade.

Path C: Interop Set (Shared Contracts)

This case covers chains sharing a single DisputeGameFactory, AnchorStateRegistry, DelayedWETH, and ETHLockbox under the interop model.

  • OPContractsManagerMigrator.migrate() forms an interop set from independent chains. It deploys the shared DisputeGameFactory, AnchorStateRegistry and ETHLockbox, and reuses the first chain's DelayedWETH as the shared one. It MAY register ZK_DISPUTE_GAME on the new shared DisputeGameFactory. The ZK_DISPUTE_GAME config MUST have a non-zero initBond, otherwise migrate() reverts with OPContractsManagerMigrator_InvalidInitBond, and a valid ZKDisputeGameConfig (see Configuration Validation), otherwise migrate() reverts with OPContractsManagerMigrator_InvalidZKDisputeGameConfig.
  • The starting respected game type passed to migrate() MUST be one that migrate() supports, otherwise migrate() reverts with OPContractsManagerMigrator_InvalidStartingRespectedGameType.
  • A set that already shares contracts registers ZK_DISPUTE_GAME through OPCMv2.upgrade() on a member (Common Mechanics step 2). migrate() reverts with OPContractsManagerMigrator_ChainAlreadyMigrated for a chain that is already in a set.
  • ZK_DISPUTE_GAME becomes the respected game type either directly through migrate(), where migrate() supports it, or later through mechanism 3.1 on a member's upgrade() or mechanism 3.2 (see Common Mechanics).
  • OPCMv2.upgrade() on any member upgrades the shared contracts for the whole set.
